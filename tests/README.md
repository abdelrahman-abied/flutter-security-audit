# Regression suite

```bash
bash tests/test.sh     # exit 0 = all green
```

No dependencies beyond what `scan.sh` itself needs (bash, grep, awk). `python3`
is used only for the `--json` assertions and is skipped if absent.

## Why this exists

Two real bugs in this scanner were found by throwaway fixtures built in `/tmp`
and then thrown away with them:

- `NET-CLEARTEXT` matched a bare `NSAllowsArbitraryLoads`, which is a substring
  of the *narrower* `NSAllowsArbitraryLoadsInWebContent` key — so an app that
  had punched one WebView-shaped hole was reported as fully cleartext.
- The six iOS checks shipped unverified; nothing had proved they fire at all.

Two more were found while writing this suite, both false *negatives*, both the
same shape — a case-sensitive pattern that no longer matches the current API:

- `WEB-JS-CHANNEL` matched only `JavascriptChannel` / `JavascriptMode`, the
  webview_flutter 3.x spelling. Every app on 4.x (`addJavaScriptChannel`,
  `JavaScriptMode`) passed clean.
- `WEB-FILE-ACCESS` matched only the property form, never `setAllowFileAccess(…)`.

All four are now assertions in section 8.

## The two fixtures

| Fixture | Contract |
|---|---|
| `fixtures/vulnerable-app/` | trips **every** check in `scan.sh` — the list in `expected/vulnerable.txt` |
| `fixtures/clean-app/` | the hardened twin: **zero** findings, absence-checks included |

Both directions matter. A check that never fires and a check that always fires
are both broken, and only the pair catches both.

`expected/vulnerable.txt` is asserted twice: against the IDs `scan.sh` declares
(so a new check without fixture bait fails the suite) and against the IDs
actually reported (so a check that stops firing fails it too). Adding a check
means adding bait to the vulnerable fixture and a line to that file.

`RES-BACKEND` is deliberately absent — it is a manual-only finding (‡) that the
scanner never emits.

## EXPECT-HIT / EXPECT-MISS

The comment-filter contract is asserted line by line, from markers that live in
the fixtures themselves:

```dart
final seeded = Random(42);            // EXPECT-HIT  code with a trailing comment
// final weak = Random();             EXPECT-MISS   prose about the bug
```

`test.sh` collects the markers with `grep -rn` and asserts that every
`EXPECT-HIT` line produced at least one finding and no `EXPECT-MISS` line
produced any. The markers sit inside comments, which the scanner strips before
matching, so they cannot influence the result. Edit a fixture and the
expectations move with it — there are no line numbers to keep in sync.

`fixtures/vulnerable-app/lib/comment_cases.dart` is the interesting file. It
covers whole-line `//` and `///`, block comments whose inner lines carry no
leader of their own, inline `/* … */` with code resuming after it, a match that
sits only in a trailing comment, and the trap: `debugPrint('https://…$token')`,
where a stripper that cuts at the first `//` loses a real finding.

Comment-awareness of *absence*-checks is asserted the same way. The vulnerable
fixture comments out its `flutter_secure_storage` dependency, its `FLAG_SECURE`
call, its `filterTouchesWhenObscured` call and its `associated-domains`
entitlement; all four checks must still fire, because a control that exists only
in a comment is not a control.

One behaviour is pinned on purpose: **a string literal is code.** `const banner
= 'Do not call Random() for tokens'` is reported. The scanner cannot tell a
hardcoded secret from a sentence about one, and the loud direction is the safe
one — but it is now a deliberate, tested decision rather than an accident.

## Notes for anyone editing the fixtures

- The vulnerable fixture's launcher activity is `exported="true"`, which is
  correct for a real app and still a finding. The clean fixture uses `"false"`
  so it can score zero without a baseline; baseline suppression is asserted
  separately, on the vulnerable fixture.
- The `SEC-CLOUDKEY` bait — a Google-API-key-shaped literal — is generated by
  `test.sh` at run time and never committed, so GitHub push protection never
  has to decide whether this repo's own fixture is a leaked credential. Running
  `scan.sh` on the fixture directory by hand will therefore report one finding
  fewer than the suite does.
- Fixture apps are not buildable Flutter projects and are not meant to be. They
  exist to be grepped.
